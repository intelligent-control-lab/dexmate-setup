Current repository: boot startup

Wrist initialization is already included. scripts/install.py --apply installs and enables wrist-camera-init.service. At boot it waits for both wrist devices, initializes them, and writes a readiness marker. active (exited) is normal for this oneshot service. It does not keep streaming: WristCameras() starts capture and triggering when your application opens it, and stops them when it closes.

Head streaming uses the vendor's dexsensor.service. The installer does not explicitly enable this service. --configure-head writes the head configuration and robot name, but does not enable or start the service. Check its state and enable it using the commands below. This is the repository's behavior; the commands inspect the robot on which you run them.

For a new robot, follow the repository Quick start with the matching vendor packages installed first. --camera-boot --activate-camera-boot builds and selects DexmateSetupHeadWrists, using /boot/initrd-dexmate-setup and /boot/tegra234-dexmate-setup.dtbo. Without --activate-camera-boot, the entry is only staged. The installer does not start services or reboot. The older HeadWrists paths in the integration record below belong to the original robot setup.

Bash · Jetson · inspect startup
systemctl is-enabled dexsensor.service wrist-camera-init.service
systemctl status dexsensor.service wrist-camera-init.service --no-pager
systemctl cat dexsensor.service wrist-camera-init.service
cat /boot/extlinux/extlinux.conf

After installation, enable both services for future boots. If a unit is reported as “not found”, install its package first: the vendor dexsensor package for the head, or this repository's installer for wrist initialization.

Bash · Jetson · enable at boot, without starting now
sudo systemctl daemon-reload
sudo systemctl enable dexsensor.service wrist-camera-init.service

Then reboot manually after reviewing the selected boot entry. To start or reinitialize cameras in the current boot, first close wrist readers and any standalone ZED viewer. These commands interrupt camera streams; they do not reboot the robot. They cannot activate a newly selected kernel overlay without a reboot.

Bash · only after closing camera readers
sudo systemctl restart wrist-camera-init.service
sudo systemctl restart dexsensor.service

If cameras do not work

Start on the Jetson to separate hardware/service problems from workstation communication. Inspect status and logs first:

Bash · Jetson · read-only diagnosis
uname -r
systemctl status dexsensor.service wrist-camera-init.service --no-pager
journalctl -u dexsensor.service -u wrist-camera-init.service -b -n 160 --no-pager
v4l2-ctl --list-devices
cat /run/wrist-cameras/ready.json
cat /proc/sys/kernel/random/boot_id
sudo journalctl -k -b --no-pager | grep -Ei 'isx031|max929|tegra.*camera|i2c|csi|vi.*error'
SymptomCheck / next step
Neither camera path works after bootCheck the selected combined boot entry, overlay and initrd. This bundle requires 5.15.185-tegra / L4T 36.5.0 and matching ZED packages. An entry in extlinux is not proof it is the one running. Inspect kernel logs and device discovery after boot.
Head service fails, or camera is busyRead the dexsensor log; verify ZED SDK / ZED Link installation and head cabling. Close standalone ZED viewers or duplicate publishers before restarting dexsensor. Keep only one owner of the head camera.
Head service runs, but RGB/depth is missingIn the head_camera block of /etc/dexmate/dexsensor/default.toml, check enabled = true, left_rgb = true, right_rgb = true, depth = true, and depth_mode = "NEURAL". Restart the service after saving. The generic ZED X One wrist entries remain disabled. In the client use configs.sensors["head_camera"].enabled = True; check ROBOT_NAME and the certificate. If local reads work but workstation reads fail, see B5.
Wrist service skipped / no wrist devicesConditionPathExists requires the combined device-tree path /proc/device-tree/bus@0/cam_i2cmux/i2c@0/tca9546@70. Check the boot overlay and driver logs. The API needs both ISX031 devices and discovers them by name; do not assume fixed /dev/videoN numbers.
Wrist probes not ready / serializer read error / GMSL link unlockedPower off before inspecting the 5 V/GND supply, CFG 0100, CSI0 → CAM1 ribbon and both GMSL links; see B2. Pins 2/4 are 5 V; pin 6 is GND. Keep the gripper's 24 V circuit separate. The bundled driver expects MAX9295 / 3 Gbps. Fix wiring or boot configuration before retrying initialization; do not guess I²C register writes.
Not initialized / marker from another bootCompare ready.json's boot_id with the current boot ID above. Close wrist readers, restart wrist-camera-init.service, and inspect its exit status/log. Do not create or edit the readiness marker manually.
Already owned / devices busyClose the other wrist application cleanly. Use sudo fuser -v /dev/video* to identify device owners; do not kill unrelated processes. The API holds both wrists under one lock, so only one reader can own them.
No fresh frame / trigger worker exitedUse the A2 WristCameras example, which starts the software trigger worker; a bare V4L2 pull does not. Check the exception, GStreamer/kernel logs and device permissions. Close the context before reinitializing.
Import / GStreamer / permission errorUse system Python 3.10 or the installed /opt/dexmate-setup/venv; check id -nG for video and i2c. Log out and back in after installation. Missing gi/GStreamer or wrist_cameras usually means missing dependencies or the wrong Python environment.

After recovery, use the A2 head + wrists example. Confirm head RGB/depth are nonempty, head source timestamps advance across repeated reads, and both wrist frame IDs increase. Service “active” and video device nodes alone do not prove frames are arriving. Do not hot-unload the camera driver stack; use the preserved boot entries and a controlled reboot for boot/driver recovery.
